# CEDex contact / morphology primary audit

Checked 2026-10-19 for the WAM-v4 design discussion. No experiment or reproduction was run.

Paper identity: **CEDex: Cross-Embodiment Dexterous Grasp Generation at Scale from Human-like Contact Representations**, arXiv [2509.24661](https://arxiv.org/abs/2509.24661), [v1 HTML](https://arxiv.org/html/2509.24661v1). Official implementation: [GeorgeWuzy/CEDex-Grasp](https://github.com/GeorgeWuzy/CEDex-Grasp), inspected revision `ef59a9fbec062b5aeedf3b7ee7e3f535718bc5a6` (2026-05-27). This Markdown is the paper's local identity and evidence entry; no separate schema file was created for this discussion.

## Published method and boundaries

CEDex generates object-surface contact intensity and a 16-part MANO assignment using a human-data CVAE. Its loss combines contact L1, part CE and KL; pretraining uses GRAB/YCB Affordance. It deliberately omits ContactGen's direction map because human/robot contact directions differ. A predefined per-hand mapping merges human contact regions **spatially on the object**, then optimizes robot configuration using part-specific SDF contact loss, surface attraction, object penetration and self-penetration penalties. [§III](https://arxiv.org/html/2509.24661v1#S3)

The data covers four hands and 500K objects, with 20M filtered grasps. Evaluation uses 10 unseen objects; mean synthesis success is 88.7%. Alignment ablation is 27.7→89.3%; physical-constraint ablation is 30.9→89.3%. Success means resistance to six force directions with <2cm displacement. Leap real-world examples are qualitative. These results concern grasp synthesis with embodiment-specific optimization; they do not establish a dynamic world model or a universal controller. [§IV–VI, Tables II/IV/V](https://arxiv.org/html/2509.24661v1#S4)

## What the official code actually supplies

- **16 parts = palm + three segments per finger.** `remap_part_labels` documents palm and each three-index finger group. `remap_contact_map` handles 16/13/10/7 robot-part configurations; the 13-part case preserves channels 0–9 and geometrically merges corresponding segments of the remaining fingers. `remap_single_channel` moves contacts toward a common object-centered direction before reassigning them to object samples. This is more than renaming or summing part channels. [utils/my_utils.py](https://github.com/GeorgeWuzy/CEDex-Grasp/blob/ef59a9fbec062b5aeedf3b7ee7e3f535718bc5a6/utils/my_utils.py#L166)
- **Labels come from hand surfaces.** The human-data preprocessing uses MANO vertices and mesh normals, virtual object-normal capsules with radius 3mm, and nearest hand-vertex part assignment. This does not reconstruct contact from a wrist/MCP/tip scaffold. [hand_object.py](https://github.com/GeorgeWuzy/CEDex-Grasp/blob/ef59a9fbec062b5aeedf3b7ee7e3f535718bc5a6/contactgen/contactgen/hand_object.py#L18)
- **Morphology is supplied explicitly.** `HandModel` loads the robot model, samples link surfaces/normals and transforms them through FK. It has per-hand link/part dictionaries plus surface-attraction and collision keypoints. Current README lists Shadow, Allegro, Barrett, Robotiq-3F and Leap; adapting another hand requires defining its mapping and keypoints. [HandModel.py](https://github.com/GeorgeWuzy/CEDex-Grasp/blob/ef59a9fbec062b5aeedf3b7ee7e3f535718bc5a6/utils_model/HandModel.py#L381), [adaptation instructions](https://github.com/GeorgeWuzy/CEDex-Grasp#adapt-to-new-hands)
- **The optimizer changes wrist pose and joints.** `q_current` contains translation, 6D rotation and joint coordinates; Adam optimizes these through FK. Contact loss gathers the assigned robot-part distance; SPF/ERF/SRF add geometry penalties. It is not a learned hand-shape latent or direct action predictor. [CMapAdam.py](https://github.com/GeorgeWuzy/CEDex-Grasp/blob/ef59a9fbec062b5aeedf3b7ee7e3f535718bc5a6/utils_model/CMapAdam.py#L59)

## Paper / implementation distinctions worth preserving

The released ContactGen trainer still trains a UV/direction branch and includes UV reconstruction/KL terms, although CEDex's paper says the downstream transfer omits the direction map. Thus the public trainer is not literally the paper's reduced two-head equation. [trainer.py](https://github.com/GeorgeWuzy/CEDex-Grasp/blob/ef59a9fbec062b5aeedf3b7ee7e3f535718bc5a6/contactgen/contactgen/trainer.py#L169)

The published SDF terminology should also not be read as an exact robot triangle-mesh signed-distance oracle: the implementation computes distances to normal-oriented capsules using sampled robot surfaces. Its function returns normalized distance-to-axis, and absent parts are initialized to zero. Audit its numerical behavior before reuse. [diffcontact.py](https://github.com/GeorgeWuzy/CEDex-Grasp/blob/ef59a9fbec062b5aeedf3b7ee7e3f535718bc5a6/utils_model/diffcontact.py#L6)

Static inspection also finds `elif robot_name == 'allegro' or 'leaphand'` in the robot-part selection, which Python interprets as always true once the Shadow branch fails. This makes subsequent Barrett/Robotiq branches unreachable there. Joint-limit penalties are stored in `self.energy`, while the differentiated return value omits them. These are source observations, not reproduced failure claims; the repository should be treated as a reference design requiring tests, not trusted drop-in code. [CMapAdam.py](https://github.com/GeorgeWuzy/CEDex-Grasp/blob/ef59a9fbec062b5aeedf3b7ee7e3f535718bc5a6/utils_model/CMapAdam.py#L21)

## Application to our WAM-v4 — inference, not a paper claim

Our [architecture contract](../../src/task/ptv3-shared-wam-v4/docs/ARCHITECTURE.md) already predicts object contact + six semantic parts. Merely increasing six parts to sixteen would not supply missing hand surfaces, link thickness, finger curvature, joint limits or reachable contact regions. The paper motivates separating shared contact intent from an embodiment-specific geometric realization.

The useful candidate decomposition is: observed hand/object state and goal → shared object-centric contact intent over time → target-hand geometry/FK and contact-region adaptation → feasible robot motion/controller. Keep the sparse scaffold as a motion reference if useful; do not use its occupancy as the sole definition of physical contact. With only wrist/MCP/tips, intermediate finger bending and surface shape are not uniquely identifiable, so denser contact labels cannot be recovered by interpolation alone.

For human data, use original meshes or richer poses where available; mark scaffold-only supervision as a lower-fidelity proximity target with provenance/masking. For robot data, derive targets from known articulated collision/surface geometry, and distinguish proximity from actual measured/simulated contact. Condition the realization stage on the target hand's actual geometry rather than assuming identical semantic fingertip trajectories imply equal contacts.

CEDex does not establish that static contact transfer solves temporal approach/closure/slip, or that C loss yields policy benefit. A local next decision should first compare current scaffold proximity against trusted mesh/simulator contact on a small existing sample, visualize disagreements, and ask whether shared contact intent can be realized by different hands. Any later implementation must connect C to execution; an unused auxiliary C head cannot itself demonstrate contact-guided control benefit.
