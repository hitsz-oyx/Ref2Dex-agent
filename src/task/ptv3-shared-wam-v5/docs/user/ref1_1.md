## 一、现在的 v5，实际上细化了什么？

当前实现不是简单把 11 点插值成 21 点，而是重新读取原始 MANO 参数、原生 21 点标注或机器人记录的关节状态，重建更完整的手部几何。模型结构可以概括为：

```text
当前与历史 H4：
    物体表面 2048 点
    双手关键点 2×21 点
    双手表面最多 2×778 点
                  ↓
          5 mm 体素化 + PTv3
                  ↓
    256 scene tokens + 42 hand tokens + 32 goal tokens
                  ↓
          12 层、1024 维共享 Transformer
                  ↓
    手：24×2×21×3 未来位移
    物体：24×32×3 未来位移
    C：24×2048×17 接触邻近/部位预测
```

**778 个手表面点用于当前几何编码，并不意味着模型预测了未来 778 点手网格；未来手运动仍由每手 21 个关键点表示。** C 的 17 个通道是一个邻近置信度加 16 个手部部位，后者为手掌和每根手指的三个分段。

这条方向合理：输入比旧骨架更能表达手掌、指节和物体之间的几何关系。不过，**空间采样更密、关键点更多，与接触标签更准、模型真正学会局部交互，是三件不同的事。**

## 二、先处理的数据与代码问题

### 1. Shadow 胶囊表面可能被多平移了一次，关节点对齐测试发现不了

**位置：`ptv3_shared_wam_v5/shadow.py → ShadowSurface.__init__()`。**

当前对 capsule 的处理是：

```python
mesh = trimesh.creation.capsule(
    radius=size[0], height=2*size[1], count=[12,12]
)
mesh.vertices[:,2] -= size[1]
```

这段代码隐含假设：Trimesh 生成的胶囊需要沿 Z 轴减去半长，才能回到局部中心。

**但在我本地的 Trimesh 4.11.1 中，生成结果已经居中。** 该版本实现直接把轮廓两端分别移动正、负半长。

我用半径 8 mm、圆柱半长 20 mm 做了最小复现：

| 状态 | 胶囊 Z 方向范围 |
|---|---|
| 应有的居中范围 | `[-28, +28] mm` |
| Trimesh 4.11.1 直接生成 | `[-28, +28] mm` |
| 执行 v5 的额外平移后 | `[-48, +8] mm` |

也就是说，在这个依赖版本下，**整个胶囊表面偏移了 20 mm**。

这里必须区分证据范围：**我确认了当前代码在 Trimesh 4.11.1 上会触发这个问题，但还没有确认远端数据准备环境的 Trimesh 版本，不能直接宣布远端 Shadow 缓存全部错误。**

#### 为什么这是高优先级？

因为当前 Shadow 测试主要比较 FK 得到的关节点与记录的旧 11 点位置。关节点来自 body transform，表面来自另外生成的 collision mesh。**关节点可以完全对齐，胶囊表面仍然偏移。** 现有测试没有验证每个 collision primitive 的表面中心与包围范围。

一旦远端触发，影响会同时进入：

- WAM 的 `dense_hand`、`dense_history`；
- 离线生成的 C 邻近置信度；
- 最近表面点对应的手指部位标签。

**建议：先在实际准备数据的环境运行胶囊边界检查。** 不要依赖库函数说明文字或固定减去半长；应明确规范化生成网格的局部中心，并检查其范围与 MJCF primitive 的预期尺寸一致。修复之后，需要重建受影响的 Shadow 手表面及其下游接触缓存，而不是只修改代码。

### 2. 修改重建代码后，重跑同一目录可能仍然沿用旧缓存

这是与上一项紧密相关的、**确定存在的工程问题**。

当前三个阶段的复用逻辑比较宽松：

**手缓存阶段**：已在 records 中完成的序列会直接跳过；存在序列 `meta.json` 时，也会直接读取旧结果。`--retry-failed` 主要重试失败项，不会强制重建已完成项。

**接触缓存阶段**：存在该序列的 `meta.json`，就复用已有接触结果，没有检查它是否对应当前版本的手表面和物体表面。

**数据冻结和训练阶段**：数据身份主要由下面两份 JSON 的内容计算：

```python
sha256(manifest_bytes + stats_bytes)
```

但 manifest 中指向的手数组、接触数组、窗口索引以及几何文件，并没有因此自动获得内容绑定。reader 也没有在读取时验证这些 payload 的摘要。

我做了一个独立反例：保持 manifest 和 stats 不变，只修改其引用的接触数组，**当前这种 identity 算法得到的摘要完全不变**。

因此，现在可能出现：

```text
修正 Shadow 表面重建
→ 在同一个输出目录重跑
→ 已完成序列被跳过
→ 接触标签继续复用
→ 最终数据身份仍被认为相同
```

**这才是最危险的“语义漂移”：文件路径、shape 和 schema 都没变，但文件代表的几何与标签版本已经不对应。**

建议每个缓存阶段绑定自己的直接输入：原始参数/机器人资产、重建协议、关键依赖版本、物体查询点身份和实际数组摘要。下游复用时检查上游身份，正常 resume 必须一致；有意修订则写入新版本目录。

还有一个相关缺口：接触生成器看到物体 `manifest.json` 就加载，并没有要求其状态为 `COMPLETED`，加载后也不会刷新。它可能接收一个 PARTIAL 几何清单，并把未覆盖物体的接触字段保留为无效。当前记录中的 2747 个物体几何已经完成，但这条代码路径本身仍需要收紧。

### 3. 冻结窗口和实际读取，对“有足够历史”的定义不一致

**位置：`freeze_dataset.py` 与 `data.py → sample_window()`。**

冻结阶段先计算：

```python
usable = joint_valid.any((1, 2))
```

然后要求 H4 的每一帧都 `usable=True`。含义是：

> 四帧中，每一帧至少有某一个有效手点。

实际 reader 则使用：

```python
start_valid = joint_valid[:4].all(0)
```

并要求 `start_valid.any()`。含义是：

> 至少有同一个语义手点，在四帧中一直有效。

这两个条件并不等价。最简单的反例是：

```text
第 1 帧：只有右手有效
第 2 帧：只有左手有效
第 3 帧：只有右手有效
第 4 帧：只有左手有效
```

冻结阶段会通过，reader 却会报 `no observed joint21 history`。这个逻辑差异已经在 CPU 最小复现中验证；**它在实际全量数据中出现多少次，我没有测量。**

建议冻结时直接采用与 reader 一致的谓词，例如对每个 tick 计算四帧逐关键点的有效性交集。更稳妥的是将窗口有效性检查抽成共享函数，避免 freeze 和 reader 各写一套。

这一项不需要重新做 MANO 重建：修正准入条件后，重新生成窗口索引和对应 TRAIN 统计即可。

## 三、架构上最值得改的不是继续加宽，而是 C 的局部信息通路

### 4. 2048 个接触查询，仍主要共享一个 64 维动态上下文

**位置：`model.py → SharedWAMV5.forward()`。**

当前接触头先分别得到：

- 物体 flow latent 的均值；
- 42 个 hand tokens 的均值；
- 全部 shared tokens 的均值。

三者各投影到 `interaction_edge_width=64`，然后与查询点编码、时间编码相加，再送入接触 MLP。

对于当前单目标物体，可以概括为：

\[
z_C=W_o\bar z_o+W_h\bar z_h+W_g\bar z_g
\]

\[
C_{t,q}
=\operatorname{MLP}\!\left(
\phi(x_q,n_q)+e_t+z_C
\right)
\]

**整个状态和 goal 对接触场的动态影响，在这个读出阶段被汇总成一个 64 维向量，供全部 2048 个查询和 24 个未来时刻共享。**

这不是说模型一定无法表达精细接触。带身份编码的 tokens 经均值汇总后，仍可能保留有用信息。但它意味着：

> v5 增加了大量局部几何输入和局部监督，C 的读出方式却仍偏向“全局条件下的空间场预测”，没有直接读取每个物体查询点对应的局部 PTv3 特征。

#### 当前代码已经有一个很便宜的改法

在 `DenseJointGeometry.forward()` 中，实际上已经计算出每个原始物体点对应的：

```python
packed[:, :count]
```

随后只取样出 256 个 scene tokens 返回；没有把完整的物体逐点特征直接提供给 C。

**建议优先返回这 2048 个逐点特征，让 C 查询读取同 ID 的局部特征。** 因为 C 查询与物体表面点使用同一组数组，可以直接按索引对应，不需要 KNN，也不需要重新做空间搜索。

第一版改动可以很小：

```text
C 查询输入
= 当前查询点位置/法向
+ 同 ID 的 PTv3 局部特征
+ 时间条件
+ 现有全局条件
```

之后再判断是否需要让查询点对 42 个手关键点做注意力读取。**我会优先做这一项，而不是继续增加 shared width、层数或查询数量。**

另外，5 mm 体素不等于模型只能达到 5 mm 输出精度，因为连续位置仍进入网络。真正需要检查的是体素聚合和读出过程有没有保留细接触所需的信息，不能单凭 voxel size 宣判精度上限。

### 5. 稠密手表面与关键点混在同一个 hand voxel mean 中

当前几何编码先区分 object 与 hand，避免物体点把手特征淹没；这一步有保留。但在 hand 内部，**21 个关键点和 778 个表面点仍被归入同一个均值分组**。

当一个体素里同时存在语义关键点和多个表面点时，关键点特征在该均值中的权重会随表面点数量下降。后面的 explicit hand 分支保留了关键点身份，所以不能说身份已经丢失；但“关键点读取到的局部交互特征”仍可能受到采样密度影响。

我把它列为**需要测量的架构风险，而不是已确认故障**。先统计关键点所在体素中的表面点数量与特征敏感性。确有影响时，再将 hand-joint mean 与 hand-surface mean 分开融合，不必立即重写整个 PTv3。

## 四、标签比 v4 更密，但目前还不能理解为毫米级真实接触

### 6. `3 mm` 不是当前部位监督的实际距离范围

接触标签使用：

\[
c(d)=\exp\left[-\frac{\max(d-3\text{ mm},0)}{10\text{ mm}}\right]
\]

超过 33 mm 截断为零。部位分类 loss 默认在 `contact_target > 0.25` 时生效。

由此算得，部位正样本可以延伸到约：

\[
d<3+10\ln4\approx16.86\text{ mm}
\]

所以，**当前 C 更准确的含义是“较宽范围的手表面邻近场及最近部位”，而不是严格的 3 mm 接触区域。**

这不是公式写错，README 也有明确说明。但如果这次升级的目标是区分很细的指节接触，就应分别评估严格近接触区域和宽邻近区域，不能只看一个整体 C loss。

### 7. 最近顶点距离，会把表面采样误差写进标签

当前离线 KD-tree 查的是最近手表面顶点，不是最近三角面。人手使用 MANO 顶点，机器人使用采样的 collision surface；两者的点密度和分布也不完全相同。

一个几何例子：查询点位于 10 mm 方形平面片的中心，并且正好贴在平面上。

- 到连续表面的距离是 0。
- 到四个角顶点的最近距离约为 7.07 mm。
- 按当前公式，邻近值约为 0.666，而不是 1。

这是独立几何示例，不是我测得的真实数据平均误差。它说明：**增加物体端查询点数量，并不能消除手表面端的离散误差。**

既然你们已经把标签计算移到离线阶段，我建议先在小批真实帧上比较最近顶点与点到三角面的距离；机器人 primitive 则可以用解析表面距离作校验。先量化在 3 mm 附近的标签翻转率，再决定是否替换全量标签算法。

还有一个需要保留的语义边界：双手表面在生成标签时被合并，输出的 16 部位标签没有左右手维度，且由最近顶点选出单一部位。因此，它不能完整表达“左右手分别由哪些部位同时作用于此处”。对单右手 Shadow 不是立即障碍，但对双手细粒度交互不能过度解读。

## 五、21 点输出与当前训练目标之间，还有一个“细化是否被奖励”的问题

### 8. 当前 loss 没有单独强调指节细节，也没有保证 τ 与 C 一致

手部仍使用按 horizon、xyz 归一化后的关键点位移 MSE；归一化统计在同一时域内由不同手和关键点共享。τ、物体轨迹和 C 仍然是并行输出，C 不读取预测 τ，也没有轨迹—接触一致性目标。

因此，下面两种情况仍然可能出现：

**整体手移动预测改善，但手指相对手掌的细节没有改善。** 单一平均 EPE 难以区分这两件事。

**C 预测出一个合理的接触区域，但 τ 中的指尖并没有到达那里。** 共享 backbone 并不会自动保证两种输出几何一致。

保留并行头本身不是错误，也不建议现在直接把 GT 未来手轨迹塞进 C 的前向输入。更合理的顺序是：先确认局部读出和标签可靠，再测量预测 τ 与预测 C 的几何一致性，决定是否加弱约束。

**目前最缺的是对应的评估。** `train_pretrain.py → evaluate()` 主要输出每源 objective、各 loss component 和整体 hand EPE，没有单独报告新增关节点、指尖、接触阶段或各时域的精度。

我建议至少区分以下几类：

| 指标 | 作用 |
|---|---|
| 根点误差与根点相对的关节误差 | 分开看整体移动与手指构型 |
| 旧 11 点、新增 10 点、指尖误差 | 判断新增表示是否真的学好了 |
| 近接触与非接触阶段误差 | 防止整体平均掩盖关键阶段 |
| 各 horizon 的手/物体误差，以及 C 部位混淆 | 判断短期执行信息与长期预测分别如何 |

这些先作为指标，不必一开始全部变成 loss。否则很容易得到“总 loss 降了，但不知道细在哪里”的结果。

还要澄清一点：**2048 个 C 查询不会自动让 C loss 变成原来的十几倍。** 目前各组件有独立有效样本分母，DDP 也补偿了梯度平均。不能仅凭查询点增多，就断言 C 已经压倒轨迹任务；需要看实际梯度和分项指标。

## 六、训练入口和配置，还有几处需要收紧

### 配置中存在“写了但没有落实”的选项

| 配置项 | 当前实现 |
|---|---|
| `save_first_step=true` | 保存条件没有使用它，完整长训不会因此自动保存第一步 |
| `checkpoint_milestone_interval=40000` | 轮转只保留最近若干 checkpoint，没有按该字段保护里程碑 |
| `hand_in_ptv3=false` | 父类保存了该标志，但 v5 重写的 forward 没有据此排除手点 |

前两项可能造成预期保留的 checkpoint 实际被删；第三项会让后续消融名义上关闭了手输入，实际上仍在使用。默认 `hand_in_ptv3=true` 时不是当前生产路径错误，但消融接口需要修复或明确拒绝这个设置。

### 现在的 v5 是独立新训练入口，不是自动继承 v4 权重

训练器创建新的 `SharedWAMV5`，目前提供的是严格 v5 `--resume`，没有看到 v4 → v5 的权重迁移入口。**复用 PTv3 代码原语，不等于复用了已经训练好的 v4 参数。** 这一点应当与“在 v4 基础上继续细化”区分。

从头训练可以是有意选择；但如果希望利用既有 v4，应单独实现、审计兼容层的 model-only warm start，新增关键点、表面编码和 C 头按明确规则初始化，不要伪装成普通 resume。

### v5 还不能直接换进旧的 565 维执行器

仓库已经明确记录，21 点 BC/RL 执行接口尚未移植。若单右手仍使用八个 60 Hz 时间点，完整 21 点 τ 是 504 维；沿用 current300 和有效位，输入将变为 **805 维**，而不是 565 维。

而且，Shadow 的旧 thumb-base 位于 `thhub`，v5 的首个拇指点改为 `thbase`。即使先投影回 11 点，也不能不加区分地套用人手的通用索引。当前对齐检查已经专门处理这个差别，执行器适配同样需要处理。

## 七、哪些实现目前是值得保留的？

这版并不是只改了维度、没有考虑数据语义。以下做法是正确的，不建议为了修问题一并推翻。

**历史与未来监督做了隔离。** 手表面输入只来自当前及过去四帧；模型前向没有读取未来手标签或未来有效性 mask。作为条件的真实 `t+24` 物体 goal 是显式训练设计，但这仍不等于部署中的空间 waypoint 已经与训练条件一致。

**缺失手表面不会被错误标成“不接触”。** 预期存在的手缺少几何时，整帧接触监督会被 mask；HOI4D 合成中间帧也不参与 C 监督。这比用零填充制造负样本稳妥。

**重建和接触计算被放在离线阶段，表面按帧缓存，而非按重叠窗口重复存储。** 原始参数约定、旧关键点对齐、float16 表面偏移量化误差都有检查；接触 head 的分块预测与梯度也有对应测试。只是这些测试尚不足以覆盖前面指出的表面位置和缓存身份问题。

仓库记录的真实 GPU smoke 是九源各一条序列构成的工程快照，batch128 完成八步更新、峰值 allocated 18.94 GiB。它证明了这套尺寸能跑，但不代表全量数据、长训或 DDP 已被验证；文档对此区分得比较清楚。

## 我建议接下来这样处理

**第一步先修数据正确性，不增加模型规模。** 核对远端 Trimesh 胶囊中心；统一 H4 准入条件；给手、物体、接触缓存补上内容与上游身份绑定。表面有问题就重建受影响的来源，不必无差别重做全部 MANO 数据。

**第二步让 C 真正读取局部几何。** 保留当前 PTv3 和共享 Transformer，先把同 ID 的 2048 个物体逐点特征接到 C head。这是我认为最贴合“做细”、也最小的一项架构修改。

**第三步用细粒度指标判断是否值得完整长训。** 保留既定 source 概率和采样规则，分别看新增关节点、指尖、根点相对构型、近接触区域与部位预测，而不是只比较总 loss。之后再处理 v5 到执行器的 21 点接口。

本次独立检查的文件在这里：minimal_repros.py[CPU 最小复现脚本](sandbox:/mnt/data/wamv5_audit/minimal_repros.py)、minimal_repro_results.json[本地复现结果](sandbox:/mnt/data/wamv5_audit/minimal_repro_results.json)。脚本不修改仓库或数据；胶囊检查应在实际准备数据的环境再运行一次。

**我的最终判断是：v5 值得继续，但当前最有价值的细化不是“更多点＋更宽网络”，而是“更可信的表面标签＋明确的局部接触读出”。先把这两层做实，再增加训练预算，结果才更容易解释。**
