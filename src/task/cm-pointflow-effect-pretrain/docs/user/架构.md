可以。按你现在这个决定，我建议把路线正式定成：

\[
\boxed{\text{30 Hz，24-step action chunk，Motus式 Simulator WM，PointWAM式 3D 编码}}
\]

也就是我们**现在只训练一个功能**：

\[
\boxed{H_t+A_{t:t+24}\rightarrow E_{t+1:t+24}}
\]

不训练 Policy，不训练 Evaluator，不预测 Y。这样以后接 Motus 很自然，但当前研究问题非常干净。

PointWAM值得借的是它把 scene + hand 都放进统一 3D 空间，用 voxel/sparse 3D 编码后做 Transformer，而不是构造显式 hand-object KNN；它本身预测的也是未来 point trajectories。[arXiv](https://arxiv.org/abs/2610.02840?utm_source=chatgpt.com)

# 1. 先把输入输出合同彻底定死

30 Hz 下：

\[
K=24=0.8s
\]

我建议一个训练窗口实际包含：

\[
\boxed{\text{过去4帧 }H+\text{未来24帧 }A,E}
\]

过去 4 帧不是为了预测过去，而是为了知道当前速度。只给 \(t\) 单帧其实对动力学是不充分的：两个物体当前 pose 一样，但一个正在上升、一个正在下降，未来完全不同。

不过模型没必要把 4 个完整场景都编码一遍。可以把历史压成当前点的：

- current position；
- velocity；
- acceleration/短历史 displacement。

于是最终仍然只有一个当前 3D scene。

### H：当前世界

统一使用**当前目标物体坐标系 \(T_t^{obj}\)**。

所有东西都变换到这个固定坐标系，整个未来 24 帧都不能再使用未来 object frame，否则会泄漏 effect。

对于每个 scene/object point：

\[
x_i,\quad n_i,\quad v_i
\]

再附加：

- object/part instance ID；
- 是否是当前交互目标；
- static/context mask。

手部使用最多两只手，每只手固定 **11 个 semantic keypoints**：

\[
6\ palm\ anchors+5\ fingertips
\]

所以最多只有：

\[
22\ hand\ points
\]

单手时另一只手直接 mask。

---

# 2. Action 就定义成 24 步 hand keypoint trajectory

这是整个架构最重要的地方。

我们不再用：

\[
a=\text{joint command}
\]

而是：

\[
\boxed{
A=\{Q^{hand}_{t+1},...,Q^{hand}_{t+24}\}
}
\]

仍然全部表示在**当前 \(t\) 时刻 object frame**。

每一个 action point token 包含：

\[
[
q_{t+\tau},
q_{t+\tau}-q_t,
q_{t+\tau}-q_{t+\tau-1}
]
\]

再加入：

- timestep embedding；
- left/right hand ID；
- keypoint ID；
- valid mask。

因此最大 action token 数：

\[
24\times22=528
\]

很小。

和以前：

\[
4096\ hand\ points
\]

然后每个 object point 做 KNN，完全不是一个计算量级。

而且这里 **不需要 KNN，不需要 2 cm hard threshold**。

---

# 3. 3D 场景编码器：按 PointWAM 思路做

我建议第一版不要直接用 PTv3，而是更接近 PointWAM 的结构：

```text
scene/object points
+
current hand keypoints
        ↓
1 cm voxelization
        ↓
Sparse 3D Conv Stem
        ↓
5×5×5 voxel patches
        ↓
Patch Tokens
        ↓
3D Transformer
        ↓
Z_H
```

PointWAM就是把 scene/hand 放入共享 3D 坐标系，然后使用 voxelized 3D representation 来预测未来场景和手的点轨迹，而不是我们之前那种显式 `1024×4096` swept KNN。[arXiv](https://arxiv.org/abs/2610.02840?utm_source=chatgpt.com)

### 1 cm voxel 不是把坐标精度截成 1 cm

这个必须注意。

每个 voxel 内我们仍然保留：

\[
\delta x=x-x_{\text{voxel center}}
\]

作为 feature。

所以网络知道：

```text
这个点属于 voxel (12,8,5)
但它实际位于 voxel 中心偏 +2.7mm,-1.3mm,+0.8mm
```

输出仍然是连续浮点坐标。

这样我们既获得 voxel 计算效率，又不会人为把 effect 量化成厘米级。

# 4. 我建议的具体 Scene Encoder V0

第一版不要做得太大。

推荐：

```text
Input point feature
    ↓
Sparse Conv 64
    ↓
Sparse Conv 128
    ↓
Sparse Conv 256
    ↓
5×5×5 patch pooling
    ↓
Linear → d=384
    ↓
8-layer Transformer
6 heads
FFN≈1536
    ↓
world tokens Z_H
```

输入 point feature 可以是：

\[
[
\delta xyz,
normal,
velocity,
object\ ID,
target\ mask,
point\ type
]
\]

point type 至少区分：

```text
scene/object point
hand keypoint
```

hand keypoint再额外有：

```text
hand ID
keypoint ID
```

我建议**第一版不要 RGB、不要 Mosaic3D feature**。

PointWAM用视觉语义是因为它做开放多任务 manipulation；我们现在只研究动力学。如果引入 Mosaic3D/RGB，反而增加 human→Isaac domain gap。

---

# 5. Action Encoder 不要 voxelize 24 个未来世界

这是我和机械复刻 PointWAM不同的地方。

A 已经是明确的候选 chunk，因此单独编码：

```text
528 action-point tokens
       ↓
shared MLP
       ↓
xyz/time/keypoint/hand embeddings
       ↓
Action Transformer 2–4 layers
       ↓
Z_A
```

推荐：

\[
d_A=384
\]

直接和 scene token 同维度。

每个 action point 保留其未来空间位置，因此模型可以学：

> 第 13 步拇指会经过物体左侧 4 mm；

而不是把整个 24-step chunk flatten 成一个 1584 维 vector。

# 6. 真正的 World Model

然后才进入我们所谓的 **Motus-style Simulator**：

\[
\boxed{
WM(Z_H,Z_A)\rightarrow Z_E
}
\]

结构可以非常简单：

```text
World tokens Z_H ───────┐
                        │
Action tokens Z_A ──────┼→ Dynamics Transformer
                        │
24 × Effect queries ────┘
                              ↓
                        future effect
```

我建议 Dynamics Transformer：

- 6 layers；
- hidden 384；
- 6 heads；
- cross/self attention；
- 整个 24-step action chunk 都可见。

**不做 causal action mask。**

因为 Simulator 的问题就是：

> “如果未来 0.8 s 已知手会这样运动，世界会怎样？”

整段 \(A\) 本来就是条件。

未来如果接 Motus Policy：

\[
H\rightarrow A
\]

才需要控制 action generation 的信息权限。

---

# 7. Effect 不建议只输出 latent

这是我们过去容易踩的坑。

主网络内部当然有：

\[
Z_E
\]

但必须挂明确的物理 supervision。

我建议 Effect 同时输出两层。

### 第一层：object/part SE(3) trajectory

对于每个当前 scene 中的刚体物体/部件，预测：

\[
\{
\Delta t_\tau,\Delta R_\tau
\}_{\tau=1}^{24}
\]

rotation 用 6D representation 输出，再转 SO(3)。

这是最重要的 effect。

---

### 第二层：解析生成 object point trajectory

已知当前 object canonical points：

\[
P_i
\]

根据预测 SE(3)：

\[
\hat P_{i,\tau}
=
\hat R_\tau P_i+\hat t_\tau
\]

得到：

\[
\boxed{
\hat F^{obj}_{1:24}
}
\]

然后直接和 GT point trajectories 做 correspondence loss。

所以我们最后既能看：

```text
translation error
rotation error
```

也能看：

```text
object point-flow EPE
```

但不用额外训练一个可能破坏刚体一致性的 dense residual head。

第一版就保持刚体结构。

---

# 8. 多物体和双手问题也一次解决

我建议 Effect 不要只预测“唯一 target object”。

OakInk2有：

```text
手
杯子
瓶盖
工具
另一个物体
```

最好把当前局部场景中的每个 rigid object/part 都形成一个 object token：

\[
O_1,O_2,\ldots,O_M
\]

然后：

\[
Z_E^{(m,\tau)}
\rightarrow SE(3)_{m,\tau}
\]

静态 object 自然应该预测接近零运动。

这样以后做 Motus Evaluator 时，它看到的是：

> 整个局部未来世界，

而不是只有一个 object displacement。

这也更接近真正的 world model。

# 9. Loss 我建议保持非常干净

总损失：

\[
L
=
L_{trans}
+\lambda_R L_{rot}
+\lambda_P L_{point}
\]

其中：

\[
L_{trans}
=
\frac1{24M}
\sum_{\tau,m}
\|\hat t_{m,\tau}-t_{m,\tau}\|_1
\]

rotation 用 geodesic：

\[
L_{rot}
=
\arccos
\frac{\operatorname{tr}(\hat R^TR)-1}{2}
\]

然后最好乘 object RMS radius，把旋转误差转换成大致表面位移量：

\[
L_{rot}^{metric}=r_{obj}\theta
\]

point trajectory：

\[
L_{point}
=
\frac1{24MN}
\sum
\|\hat P-P^{GT}\|_1
\]

**先不加 contact loss、不加 Y、不加 value、不加 contrastive action loss。**

否则第一版又开始复杂化。

# 10. 时间监督：24步全部训，不再区分 single/chunk 模型

主合同：

\[
A_{1:24}\rightarrow E_{1:24}
\]

所有未来步都监督。

评估时单独报告：

\[
\tau=1,4,8,12,24
\]

这样我们可以看到误差随 horizon 怎么积累。

但不再训练：

```text
one-step Cm
然后再训练 chunk GRU
```

就是一个模型。

# 11. 数据坐标合同非常重要

每个 window 的 current object frame 固定为：

\[
T_t
\]

然后：

\[
x^{local}=T_t^{-1}x^{world}
\]

对：

- 当前 scene；
- 当前 hand；
- **未来 24 步 hand action**；
- **未来 24 步 object effect**

全部使用这个同一个 \(T_t\)。

千万不要未来每一帧重新 object-centric：

\[
T_{t+\tau}^{-1}
\]

那样就会把 object motion消掉，甚至给 action 泄漏 GT effect。

这一点必须写成 dataset hard assertion。

---

# 12. 单双手数据合同

最多两手：

\[
Q\in\mathbb R^{2\times11\times3}
\]

action：

\[
A\in\mathbb R^{24\times2\times11\times3}
\]

并有：

\[
mask\in\{0,1\}^{24\times2\times11}
\]

所以：

```text
单手：
right valid
left masked

双手：
right valid
left valid
```

模型完全同一套。

不拆双手 trajectory。

---

# 13. 数据采样不要让“零运动”淹没模型

OakInk2 全部滑窗的话，很容易大量出现：

```text
手在移动但物体不动
静止
准备阶段
离开阶段
```

如果 90% 都是零 effect，模型学：

\[
E=0
\]

就会很好看。

所以**不是删掉无效数据，而是控制采样比例**。

第一版我建议大概：

- 60%：物体有明显 effect / interaction；
- 20%：手靠近/接触但物体 effect 较小；
- 20%：真正 zero-effect negative。

这样模型既学物理响应，又知道什么时候“不发生任何事”。

这比以前硬 2 cm gate 更合理。

---

# 14. 为以后 Motus 预留什么？

其实只需要现在把 token 类型设计好：

```text
[WORLD]
[ACTION]
[EFFECT_QUERY]
```

当前预训练：

\[
[WORLD]+[ACTION]\rightarrow[EFFECT]
\]

以后 Policy：

\[
[WORLD]+[ACTION\ QUERY]\rightarrow A
\]

以后 Evaluator：

\[
[WORLD]+[ACTION]+[EFFECT]+[VALUE\ QUERY]\rightarrow Y
\]

**backbone 和数据表示不用换。**

这就是为什么你现在定 `24-step action chunk` 是合理的：以后 Motus 里 Policy 直接生成这 24 步 keypoint chunk，Simulator 就是今天训练的这个 WM。

## 最终 V0 我会冻结成这个配置

| 模块 | V0 |
|---|---|
| 频率 | **30 Hz** |
| action horizon | **24 steps / 0.8 s** |
| H history | 过去 4 帧压成 motion feature |
| hand | **11 keypoints / hand，最多双手22点** |
| scene | 当前局部 object/scene points |
| voxel | **1 cm** |
| patch | **5×5×5 voxels** |
| scene backbone | sparse conv + Transformer |
| hidden | 384 |
| scene Transformer | 8 layers |
| action tokens | 最多 528 |
| action encoder | 2–4 Transformer layers |
| dynamics | 6-layer Transformer |
| effect | 24-step object/part SE(3) |
| auxiliary effect | structured object point trajectory |
| KNN | **没有** |
| 2 cm hard gate | **没有** |
| contact head | **暂时没有** |
| Y/value | **暂时没有** |
| Policy | **暂时没有** |

一句话概括就是：

\[
\boxed{
\text{PointWAM式3D世界编码}
+
\text{24-step hand-keypoint action chunk}
+
\text{Motus式 action-conditioned Simulator}
}
\]

而且我认为现在**不要再把 OI-Cmv2 的 KNN/contact-token 结构带进来**。先让这个简单、可规模化的 WM 在 OakInk2 上证明：

\[
\boxed{A\text{真的能改变并提高对 }E\text{ 的预测}}
\]

最关键的第一组对照就是：

\[
H\rightarrow E
\]

vs.

\[
H+A\rightarrow E
\]

再加：

\[
H+\operatorname{shuffle}(A)\rightarrow E
\]

如果大数据下这三者都拉不开，那才说明我们的 action representation/数据本身有问题，而不是继续调局部 KNN。
