我把当前 main 里的 PointWorld 主线、三源训练、时序修正版、DDP、归一化，以及 PointWorldWAM 的后续接口都顺了一遍。结论是：现在 PointWorld 不是“整体实现错了”，时序保持、mask、刚体输出、DDP/checkpoint 这些反而做得比较扎实；但有两个我认为必须优先修的实现问题，另外有几个会直接影响我们后续“想象→评估→规划”结论的问题。
1. P0：体素坐标原点的实现有问题，而且之前没有被测试覆盖。
   在 src/task/cm-pointflow-effect-pretrain/src/oakink_wm/pointworld.py 和 pointworld_temporal.py 里都有：
   coords = coord[exists].float()grid = torch.floor((coords - coords.amin(0)) / .01).long()
   
   
   这里的 coords.amin(0) 是对整个 microbatch 的所有 scene 点 + 所有未来 action 手点求最小值。于是出现两个问题。
   第一，候选动作会改变当前场景的体素划分。我们只是换一个未来手轨迹 \(a\)，理论上当前状态 \(H\) 应该保持不变，但如果新的手点改变了 amin，当前物体点落在哪个 voxel、如何 pooling、Hilbert 序列都会跟着变。这样 action 不仅通过“动作条件”影响预测，还偷偷通过改变场景离散化影响预测。
   第二，同一个样本会依赖它和谁组成 batch。主三源训练目前是每 rank microbatch=64，但验证明确用了 validation_microbatch=2。因此训练和验证时，同一个样本的 voxel grid phase 可能不一样。这是一个真正的 train/eval mismatch。
   现有 test_pointworld_temporal.py 检查了 time identity、重复 sparse index、mask、未来 effect 不泄漏、action-time sensitivity 等，但没有检查 batch-composition invariance。所以这个问题目前没有被自动测试挡住。
   我认为这个要先修。体素原点应该由固定坐标系/当前场景单独确定，绝不能由候选未来 action 或同 batch 的其他样本决定。最稳的是用 anchor frame 下固定 workspace voxel grid；至少也应该是 per-sample、scene-only origin。修完必须加一个测试：同一样本单独推理、和两个完全不同的样本拼 batch，输出应基本一致。
   
   
当前 pretrain 对静止物体的预测确实有明显问题，而且不只是精度稍差，而是出现了系统性的“假运动”。

不过，我认为现在还不能直接归因于模型架构不行。检查现有工程实现后，我更怀疑是运动样本采样、损失加权、模型选择标准共同造成了运动偏置，再叠加可能存在的体素化问题。

## 1. 静止预测到底有多差？

这是仓库目前 HOCap 外部测试的实际结果，预测跨度为未来第 24 帧。

| 模型           | 静止物体点误差   | 运动物体点误差   |
| ------------ | --------- | --------- |
| 静止保持基线       | 0.356 mm  | 74.744 mm |
| OakInk2 单源模型 | 8.039 mm  | 30.692 mm |
| 三源混合训练模型     | 22.160 mm | 19.690 mm |

这里的“静止”是接近静止，而非物理上绝对静止；数值来自 HOCap 自然采样面板的 17 个静止窗口与 47 个运动窗口。HOCap 帧率尚未核实，因此这里只按第 24 帧比较。

这张表说明了一个很明确的现象：

- 运动预测改善了：三源模型比单源模型更准确。
- 静止预测却退化了：误差从 8 mm 上升到 22 mm。
- 简单假设物体保持不动，误差反而只有 0.356 mm。

但需要注意：22 mm 是未来物体表面点位置误差，不等于预测的物体平移一定有 22 mm。旋转误差也会贡献表面点误差。

另外，这并不证明三源数据有害。因为两个模型的训练步数、batch 和损失配方都不同。

我的判断：当前模型已经学到一定的手物运动关系，但没有很好地学会“什么时候应该预测物体不动”。

## 2. 工程实现有没有问题？

有。我把问题分成“已确认的训练设计问题”和“需要实验确认的工程缺陷”。

问题 A：静止样本的监督权重过低

高优先级

目前 `pointworld_temporal.py` 采用：

\\[ w=0.1+0.9\sigma(5(r-1)) \\]

对近乎静止的物体，\\(r\approx0\\)，得到：

\\[ w\_{\mathrm{static}}\approx0.106 \\]

而明显运动的物体，权重接近 1。

也就是说，单个静止点产生的误差，在加权前数值相同的情况下，贡献只有运动点的约十分之一。

代码确实保留了 `motion_floor=0.1`，所以没有完全忽略静止样本，但这不代表静止监督足够强。

依据：`src/oakink_wm/pointworld_temporal.py` 中 `motion_weights()`。

问题 B：模型选择标准进一步放大运动偏置

高优先级

`train_oakink2_pointworld_ddp.py` 中，best checkpoint 的分数为：

```
score = measured[    'model/anchor/cat0/h24/point_epe']
```

也就是只依据运动类别中的锚物体，在未来第 24 帧的预测误差选择模型。

静止误差即使越来越大，只要运动预测有所改善，仍然有可能被选为 best。

这是训练目标与模型筛选目标共同偏向运动，而不是一个偶然现象。

问题 C：体素化依赖其他样本及候选动作

待量化

当前仍然使用：

```
grid = torch.floor(    (coords - coords.amin(0)) / .01).long()
```

这是我上一轮发现的工程问题。因为 `coords` 包含未来手点且跨整个 batch，样本配对或候选轨迹变化会改变网格原点。

但必须区分：这是明确的实现风险，不代表它已经被证明是静止误差 22 mm 的原因。

最小验证是固定一个完全相同的静止样本，改变 batch 内其他样本以及候选动作，比较预测。如果差异达到毫米级，就有充分理由优先修复体素化。

问题 D：时间特征可能诱导固定的运动趋势

需要消融

当前预测头为：

```
raw = self.head(    query[:, :, None]    + self.time.weight[None, None]    + action_query[:, None])
```

然后直接回归 24 帧相对于当前状态的 SE(3) 变换。

这个结构本身没错。但它没有显式的“保持不动”约束。即使动作对物体没有有效作用，模型依然可以通过时间 embedding 和数据中的平均运动模式，输出持续增大的位移。

这可能解释为什么越远的预测时间，静止物体越容易漂移；但还需要查看逐帧误差才能确认。

## 3. 应该如何改善？

我不建议立即换架构，也不建议马上重新训练全部 50000 步。

建议先做一个很小的定向消融。

| 修改                        | 目的           | 优先级 |
| ------------------------- | ------------ | --- |
| 静止样本权重从约 0.1 提到 0.5 或 1.0 | 让模型认真学习不动的情况 | 高   |
| 验证时同时记录 moving/static 误差  | 避免改善一边、破坏另一边 | 高   |
| 修复体素原点，保证同一样本输入稳定         | 排除实现层面的随机漂移  | 高   |
| 对静止样本增加零位移监督              | 减轻预测偏移       | 中   |
| 引入显式的运动/静止门控              | 进一步降低假运动     | 后续  |

### 第一阶段：先不改架构，只做损失实验

选当前 `best46000.pt` 或 `final50000.pt` 作为共同初始化，冻结训练/验证样本和其他超参数，比较：

- A：原 `motion_floor=0.1`
- B：改为 `motion_floor=0.5`
- C：改为 `motion_floor=1.0`，相当于不再按运动幅度区分权重

注意：这几个值是消融候选，不是已经验证的最佳参数。

三组都使用新的输出目录短程微调，同时报告静止误差、运动误差和运动样本优于 persistence 的比例。最好使用同一组固定验证样本，并按序列分组统计置信区间，避免少量静止窗口误导结论。

我认为这里最有价值的是 `0.5`。因为直接全设成 1，可能使大量几乎不动的点主导优化；而 0.5 可以先检查是不是监督强度不足。

### 第二阶段：如果损失调整还不够

才考虑显式的“物体是否会动”的预测分支。

例如：

\\[ \hat E=\mathrm{Blend}\left(I,\hat E\_{\mathrm{dynamic}},p\_{\mathrm{move}}\right) \\]

其中 \\(I\\) 表示恒等刚体变换，\\(p\_{\mathrm{move}}\\) 表示预测该物体在给定动作下发生有效运动的概率。

这样模型可以先判断是否运动，再预测运动幅度。

但这会增加模型结构和训练复杂度，而且需要保证概率预测由当前状态和候选动作决定，而不是利用未来物体状态。我不会把它作为第一步。

## 4. 一个更重要的问题：现在是不是在错误地把“预测物体会动”当成模型能力？

从三源实验结果看，这是我真正担心的。

当前训练条件是真实未来手轨迹。在运动样本中，手经常会随着物体一起移动；模型可能学会了一个很强的相关性：

> 未来手移动得多，未来物体也应该移动得多。

但它是不是学会了：

> 手移动了，但是没有抓住物体，所以物体应该保持不动？

这一点现在还没有被充分验证。

这比静止 EPE 本身更关键，因为我们的规划器以后必须区分成功推动物体的动作和手从物体旁边经过的动作。

因此，我建议补一个非常具体的检查：在 HOCap 或 GRAB 的现有样本里，分离出“手明显运动，但物体基本静止”的窗口。比较模型误差与“手物一起运动”的窗口误差。

如果前者特别差，那么问题就不是单纯的 loss weighting，而是模型没有充分学会接触条件下的因果区分。那时才需要针对非接触、滑移、接触失败的样本补数据。

## 5. 最终判断

| 问题                   | 我的判断                        |
| -------------------- | --------------------------- |
| 现在静止预测是否很差？          | 是，HOCap 外测已经显示明显退化          |
| 有确定的代码崩溃或标签计算错误吗？    | 目前没发现可直接确认的错误               |
| 训练设计是否有问题？           | 有，静止监督与 checkpoint 选择都有运动偏置 |
| 需要换掉 PointWorld 架构吗？ | 目前没有依据                      |
| 需要立即从零重新训练吗？         | 不建议                         |
| 能否通过短程微调修复？          | 有可能，必须做消融验证                 |

我建议下一步只做一件事：静止运动分层诊断 + 三组损失权重微调。

先保证现有 PointWorld 不会对稳定物体凭空预测运动，再去继续扩充数据和连接 evaluator。否则我们的规划器可能会把“想象中会移动”的候选误认为真正有效的候选。

核心目标不是把静止误差刷到 0，而是同时保持运动预测优势和静止预测可靠性。这才是一个可以参与动作决策的世界模型。
