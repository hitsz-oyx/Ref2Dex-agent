## 一、修复后还有一个 BC 训练问题

我进一步检查了 v3 的 [`train_measured_scheduled_bc.py`](https://github.com/hitsz-oyx/Ref2Dex-agent/blob/a4b74675/src/task/wam-rl-policy-v3/tools/run/train_measured_scheduled_bc.py?utm_source=chatgpt.com)，发现当前 Scheduled686 训练依然只保留 `tau_valid=True` 的样本：

```
ids = np.flatnonzero(valid)
```

这样有一个实际影响：WAM 历史不足时，Scheduled BC 没有训练监督。

正常在线执行的前3个控制拍，H4尚未建立，必须使用：

\\[ \tau=0,\qquad valid=0 \\]

但当前训练只使用 `valid=True` 的样本。这意味着训练过程中网络可以不断调整共享权重，却没有训练样本约束 `valid=False` 时的动作行为。

对照现有样本数量，这个问题尤其明显：

| TRAIN数据              | 行数     |
| -------------------- | ------ |
| Current421 已准入命令     | 54,162 |
| 新 τ 有效命令             | 52,660 |
| 未进入 Scheduled BC 的命令 | 1,502  |

501条 TRAIN 序列，每条最初约3拍不具备完整H4；与被排除的1502行基本吻合。

我的判断是：这是一个确定存在的训练覆盖缺口，但还不能断言它已经造成实际失败。

修复建议不是伪造启动阶段的 τ，而是在 Scheduled BC 训练中保留这些真实样本，按 `tau=0, valid=0` 处理，并使用同一时刻的动作标签监督。这样才真正训练了部署时必然发生的启动状态。

同时，想证明 WAM 的增益，Current 和 Scheduled 最好还增加一组完全相同训练样本集合的对照，否则数据准入差异也会影响比较。

## 二、事件调度器仍有一个恢复边界问题

在当前 [`task_scheduler.py`](https://github.com/hitsz-oyx/Ref2Dex-agent/blob/a4b74675/src/task/wam-rl-policy-v3/src/wam_rl_policy_v3/task_scheduler.py?utm_source=chatgpt.com) 中，计划事件游标在状态转移前依据实测 `released` 边沿推进。

考虑这个过程：

```
ACQUIRE → TRACK
计划下一个事件：RELEASE

实际发生意外失手
grasp_lost=True、released=True

计划 RELEASE 被确认
event_index 前进

执行阶段回到 ACQUIRE
但计划下一事件可能变为 NONE
```

也就是说，重新抓取所需的 CONTACT 意图可能与计划事件游标不一致。

这是代码路径上可以构造的逻辑问题。不过当前 WAMv4 没有消费事件字段，所以它不是现阶段 Scheduled686 表现差的已证实原因。

建议补一条真实状态机测试：抓取成功→搬运中掉落→重新建立抓取→继续搬运，检查阶段和下一事件是否始终一致。

## 三、剩余的主要风险已经转向 BC 本身

目前原生接口方面的证据相对充分：物理248维观测、canonical动作到PD目标、episode隔离都通过了工程检查。修复后，离线/在线的 goal 点位移一致性也经过验证。

但尚有三个关键问题没有形成正向证据。

第一，Current421 仍是弱控制基线。 已有最优离线MAE为0.038258，但旧300拍闭环无法推进物体路径。零扩展能保留它的输出，却不能让它自动获得稳定抓取能力。

第二，任务目标不包含完整的手部操作方式。 DExplore teacher 原来利用手部参考来决定具体如何接近、闭合和操纵。同一个物体运动目标下，不同手部操作可能对应不同命令。当前 task10 只明确物体目标和阶段；WAM τ 负责补充未来手运动信息。因此 Current421 本身可能存在不可辨识性，而新 Scheduled686 才是更值得检验的版本。

第三，离线 BC 和在线闭环仍需要做逐拍对应分析。 现在保证了目标字段一致，并不代表学生稍有偏差后，生成的阶段、局部目标与动作仍然处于训练分布。尤其值得比较抓取前10～30拍的实际手轨迹、动作方向和条件变化。
