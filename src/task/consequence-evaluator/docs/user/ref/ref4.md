我建议把方案固定为：

> **先用 GRAB 训练“抓取阶段与进度评估器”，验证真实未来 E/I 的帮助；再保持评估器不变，将 GT 替换成 PointWorld 预测；最后通过“关节目标轨迹 → 手部几何轨迹 → 世界模型 → 评估器”的接口接入机器人决策。**

**第一阶段不需要 fork，不依赖严格同状态偏好对，不训练长期 Q，也不重新训练 PointWorld。**

下面给出完整实现规格。源码依据是当前 `main/c594f6a`；涉及新增模块的内容是我的设计建议，不是仓库已经实现的功能。

## 一、先固定我们到底在学习什么

### 1. 任务范围

第一版只做：

**多个 GRAB 物体上的单手抓取：接近 → 建立抓持 → 抬升 → 保持。**

不把使用物体、换手、主动放回混进同一个进度标尺。先从 GRAB 的 `lift` 类原始轨迹筛选，而不是直接使用以前经过机器人重定向筛选的少量轨迹。

GRAB 原始文件有手部运动、物体刚体位姿、桌面网格及位姿、接触标注。桌面高度可能随轨迹变化，接触标注来自几何接近等判据，并非接触力。它们足以支持阶段标注，但不能直接提供机器人抓取稳定性的完整物理真值。

### 2. 评估器的输出

评估器输出未来每一帧的：

- **阶段**：接近、建立抓持、抬升、保持。
- **进度**：统一标尺下的 \(p_k\in[0,1]\)。

这里必须明确：

**进度不是成功概率，不是长期累计回报，也不是最优动作价值。**

第一轮要回答的是：

> 同样给定当前情况和手部运动，加入物体未来后，模型是否更准确地判断这段抓取进行到了哪里？

再回答：

> 用 PointWorld 预测的未来，能保留多少这种能力？

不再要求评估器预测输入窗口之外的长期结局。**评价一段未来时，使用这段未来生成监督标签是正常的奖励模型训练；不能做的是把标签预测准确率直接当作动作选择收益。**

## 二、视频方法中，哪些架构值得借鉴

这次我核对了论文方法和部分实际代码。建议借鉴的是具体组件，而不是把几个完整系统拼起来。

| 工作 | 经过核对的方法 | 我们借鉴什么 |
|---|---|---|
| **SARM** | 从阶段边界生成统一进度标签；分别估计阶段及阶段内进度。主要实验是衣物折叠，不是灵巧手抓取 | **阶段标注与进度标尺**；阶段信息辅助细粒度评分 |
| **ReWiND** | 图像和语言编码后，使用因果时序 Transformer，逐帧输出奖励；用局部倒放训练进度下降 | **逐帧输出、因果时序建模、倒退增强**；避免仅凭时间位置猜进度 |
| **PROGRESSOR** | 用初始、当前、目标观测估计进度分布；另用在线数据处理分布外高分问题 | 提醒我们保留任务上下文，并且**不能把示范上的高分当作失败识别能力** |
| **DexWM** | 灵巧手世界模型；规划时在机器人关节空间生成候选，再通过 FK 转换成手部关键点动作 | **机器人动作接口**，不是奖励监督方法 |

对应原始依据：SARM 论文及 LeRobot 实现、ReWiND 附录、PROGRESSOR 项目说明、DexWM 规划附录。[arXiv](https://arxiv.org/html/2509.25358v1)

**我的架构选择：小型几何编码器＋时序 Transformer＋阶段/进度双头。**

我们已经有三维手物信息，没有必要为了模仿视频方法，先渲染图像，再加载一个视觉语言大模型。

## 三、整体架构：三条路径共用同一个物理接口

```text
                         ┌──────────────────────┐
当前几何与历史 H ────────→│                      │
任务上下文 C ───────────→│     Evaluator         │──→ 逐帧阶段、逐帧进度
手部轨迹 A ─────────────→│                      │──→ 片段评分 S
                         └──────────↑───────────┘
                                    │
                              统一 FutureBundle
                                    │
                 ┌──────────────────┼──────────────────┐
                 │                  │                  │
              E0 对照          Oracle 路径          预测路径
            不提供 E/I         真实 E/I             PointWorld
                                                    ↓
                                                 预测 E
                                                    ↓
                                             结合 A 计算几何 I
```

**Oracle 与预测路径只替换 `FutureBundle` 的来源，不更换评分目标、坐标系、评估器输入格式。**

另外，评估器不能直接使用 PointWorld 中已经融合候选动作的内部特征作为“公共历史 H”。否则 E0 与其他组的输入边界会变得不清楚。第一轮使用独立、轻量、只读取当前及历史几何的编码器。

## 四、与当前 PointWorld 对齐的接口

### 4.1 当前实际接口是什么

我重新检查了 `oakink_wm/data.py`、`multisource.py` 和 `pointworld_temporal.py`：

| 项目 | 当前 PointWorld |
|---|---|
| 频率 | 30 Hz |
| 历史 | 4 帧 |
| 未来 | 24 帧，即 0.8 秒 |
| 手部 | 右、左两个槽位，每手 11 点 |
| 动作 | 每个手点 9 维：位置、相对当前位移、逐帧位移 |
| 输出 | 每个物体未来 24 帧的旋转和平移 |
| 坐标系 | 整个窗口固定在**当前目标物体坐标系** |

实际动作张量可写成：

```text
[B, 24, 22, 9]
```

模型内部再整理为：

```text
[B, 24, 2, 11, 9]
```

左右手顺序是 `right, left`。输出不是接触力，也不是一个通用价值潜变量。

### 4.2 新评估器直接继承这套 A，不再使用 18 维残差

第一阶段统一使用：

```text
A_geo: [B, 24, 22, 9]
A_valid: [B, 24, 22]
```

单帧展平后是 **198 维**，不是原 evaluator 的 18 维。

当前 `consequence-evaluator/model.py` 的动作投影是 `Linear(18, width)`，不能原样接 PointWorld。因此需要新建几何动作投影，不能仅仅把输入字段改名。

即使首版只保留单右手参与抓取，也保留两个槽位与掩码。另一只手是否输入，应与对应 PointWorld 样本保持一致；不能把有效的零坐标当作“手不存在”。

### 4.3 E 的定义

令当前目标物体位姿为 \(T_{o,t}\)，未来位姿为 \(T_{o,t+k}\)，则目标物体的：

\[
E_k=T_{o,t}^{-1}T_{o,t+k}
\]

保存为：

```text
E: [B, 24, 4, 4]
```

送入评估器前，取前 3 行并按固定顺序展平：

```text
E12: [B, 24, 12]
```

**这个 E12 是刚体变换矩阵的 12 个数，不是旧实验中包含速度差的 E12。维度相同，不代表语义相同。**

当前 PointWorld 支持多个局部物体，因此适配器必须按目标标记取出正确的 `target_slot`，**不能假设第 0 个物体永远是目标**。对于非目标物体，其变换关系还包含当前局部位姿，不能无条件套用上面的简化公式。

### 4.4 I 不需要先增加预测网络

A 中已经包含未来手点在当前目标物体坐标系下的位置 \(P_k\)。对目标物体：

\[
I_k=R_k^\top(P_k-d_k)
\]

其中 \(R_k,d_k\) 来自 E。

因此：

```text
I_geo: [B, 24, 22, 3]
```

完整双手接口中，每帧未来槽为：

```text
E12 + I66 = 78 维
```

只有单手有效时，有效的手物几何仍然是 33 维，其余由掩码屏蔽。

**这意味着 Oracle-EI 相比 Oracle-E，不是增加独立的物理观测，而是把 A 与 E 的相对关系显式算出来。** 它检验的是这种表示是否更容易学习，不是“接触信息是否有用”。

后续使用预测 E 时，也必须重新计算：

\[
\hat I_k=\hat R_k^\top(P_k-\hat d_k)
\]

不能出现“E 换成预测值，I 仍然使用真实物体位姿”的半 Oracle 实验。

### 4.5 必须补充任务上下文 C

这是此前方案中遗漏的重要接口。

**在当前物体坐标系里，物体无论在桌上还是已经举起来，都可能位于原点。只看局部手物几何，不能可靠区分这两种状态。**

因此，评估器额外接收：

```text
support_plane_current_frame   # 桌面平面在当前物体坐标系中的表示
object_scale                 # 物体尺度
task_lift_clearance           # 本任务要求的抬升间隙
```

支撑面从原始 GRAB 桌面网格和位姿读取；机器人阶段从环境观测或已知桌面配置取得。**不能默认所有序列桌面高度都是 0。**

C 对三组完全一致，只包含决策时已知信息。不输入真实阶段、真实进度、完成时间、未来目标帧或序列编号。

## 五、GRAB 标签具体怎么制作

### 5.1 数据来源和筛选

使用当前 PointWorld 所对应的 GRAB 原始序列，新增标签侧文件，不重做整个几何预处理。

首版筛选条件：

**明确的 lift 意图、目标物体刚性、主要由右手操作、包含接近至抬升保持过程、没有另一只手或身体部位承担主要支撑。**

主动放回之前结束片段。多次重试、阶段边界不清楚的部分先屏蔽，不强行贴单调进度标签。

当前 PointWorld 的通用加载器读取手、物体位姿、有效性等字段，但没有直接加载原始 GRAB 的桌面和细粒度接触标签。**因此这些字段需要从原始数据补读，不能假设当前训练缓存已经齐全。**

### 5.2 每条片段标四个边界

| 边界 | 含义 | 获取方法 |
|---|---|---|
| \(b_0\) | 有效接近开始 | 自动提出运动起点，人工确认 |
| \(b_1\) | 接触建立 | 原始接触标注及持续性 |
| \(b_2\) | 物体离开支撑面 | 物体网格与桌面几何关系 |
| \(b_3\) | 进入目标抬升保持区间 | 达到目标间隙，并在随后一段时间保持接触与离面 |

建议以以下数值作为**标注工具的初始候选参数**：

```text
持续接触：3 个控制帧
离面候选：物体底部距桌面超过 1 cm
目标抬升候选：超过 3 cm
保持确认窗口：15 帧，即 0.5 秒
```

这些不是论文规定的通用物理标准。先在训练集的一小批序列上人工核查，再冻结标注配置，不能根据测试结果修改。

这里有两个细节：

**第一，\(b_3\) 是经过保持验证的“目标区间进入时刻”，不是把整段等待保持的时间都当作进度增长。** 一旦进入保持阶段，进度固定为 1，避免物体不动但分数自动上涨。

**第二，保持确认是示范标签质量检查，不是给模型提供真实未来接触力，也不代表它已经会预测掉落风险。**

### 5.3 生成统一进度

对接近、建立抓持、抬升三个阶段，按照 SARM 的方法，在训练集统计平均阶段时长比例 \(\alpha_s\)。阶段内部插值得到：

\[
p_t=
\sum_{j<s}\alpha_j+
\alpha_s\frac{t-b_s}{b_{s+1}-b_s}
\]

保持阶段 \(p_t=1\)。验证和测试沿用训练集的 \(\alpha_s\)，不各算一套。SARM 的阶段标尺正是为了解决不同示范速度导致的进度标签不一致。[arXiv](https://arxiv.org/html/2509.25358v1)

保存：

```text
stage[T]             # 0/1/2/3
progress[T]          # 0~1
label_valid[T]       # 不确定帧不参与监督
phase_boundaries
annotation_version
source_sequence_id
source_frame_mapping
```

**这些是阶段归一化的弱监督，不应包装成精确物理价值 GT。** 阶段内部仍可能存在停顿和速度差异，因此除了总体进度误差，必须单独检查阶段识别与阶段内误差。

### 5.4 防止时间对齐错误

原始 GRAB 是 120 Hz，当前 PointWorld 使用 30 Hz。标签必须通过原始时间戳或已保存的转换映射，与现有几何样本连接。

特别注意：当前 `SourceWindows` 为兼容加载器会重建一套 `frame_ids`。**不能直接把这套内部编号当作原始 GRAB 帧号去读取接触标签。**

## 六、Evaluator 的具体网络

### 6.1 不加载视频大模型，改用几何输入

推荐配置：

| 部分 | 实现 |
|---|---|
| 当前物体几何 | 小型 PointNet：共享 MLP＋掩码池化 |
| 历史 | 4 帧手物几何，分别投影成时序 token |
| A 分支 | 每帧 198 维几何动作＋有效性掩码 → 128 维 |
| E 分支 | 每帧 12 维 → 128 维 |
| I 分支 | 每帧 66 维＋有效性掩码 → 128 维 |
| 上下文 C | 小 MLP → 128 维 |
| 时序主干 | 2 层 Transformer，宽度 128，4 个注意力头 |
| 阶段头 | 4 类分类 |
| 进度头 | 10 档分布，取期望得到连续进度 |

这是**借鉴 SARM/ReWiND 的结构原则，对三维几何做的小型实现**，不是照搬它们的模型规模。

当前 evaluator 已有 128 维、两层 Transformer 和 10 档进度头，可以复用这些基础组件；但输入投影、阶段头和数据加载需要修改。

### 6.2 时序规则

采用因果掩码：

> 第 \(k\) 帧的进度输出，只读取历史以及未来片段中第 1 至 \(k\) 帧的信息。

这样当前进度 \(\hat p_t\) 不会因为替换候选未来而改变，也方便以后对真实执行过程逐帧评分。

可以使用相对当前时刻的时间位置，但**不输入原始视频的绝对帧号、总时长或剩余完成时间**。ReWiND 专门讨论了完整位置编码带来的时间捷径问题，并采用因果时序聚合。[arXiv](https://arxiv.org/html/2505.10911v1)

阶段预测的软概率可以投影后辅助进度头，但不能把 GT 阶段作为训练时输入、测试时再换成预测阶段。

### 6.3 损失与评分

首版只用：

\[
L=L_{\text{stage-CE}}+L_{\text{progress-soft-CE}}
\]

进度标签落在两个相邻档位之间时，按距离分配软标签，这部分可以沿用当前进度损失。

**暂时不使用必须依赖两条匹配轨迹的排序损失。**

片段评分不另训练一个无监督的标量头，直接由进度得到：

\[
S(H,A,F,C)
=
\frac{1}{24}\sum_{k=1}^{24}\hat p_{t+k}
-\hat p_t
\]

对于同一决策状态，\(\hat p_t\) 对所有候选相同，因此这个排序与平均未来进度一致；它的解释是“这段动作预计带来多少平均进展”。

当前模型的独立 `score` 头依赖配对损失学习。切换成逐帧监督后，**应删除或停用它，不能保留一个没有有效监督的评分头参与决策。**

### 6.4 倒退增强

借鉴 ReWiND，对少量训练片段局部倒放，让进度标签随原帧下降。[arXiv](https://arxiv.org/html/2505.10911v1)

在三维实现中，必须同步重建手和物体轨迹、A 的位移特征、E/I，不能仅仅反转标签。

这类样本明确标成 `augmentation`：

**只训练评估器，不训练 PointWorld，不称为真实物理失败，也不进入主要测试集。**

## 七、第一轮实验怎么安排

### 7.1 三个正式对照

| 实验 | 输入 | 检验内容 |
|---|---|---|
| **E0** | H、A、C | 不提供物体未来时的能力 |
| **Oracle-E** | H、A、C、GT-E | 真实物体运动是否有增益 |
| **Oracle-EI** | H、A、C、GT-E、GT-I | 显式相对几何是否更好学习 |

三组模型保留相同输入槽、容量、初始化、样本抽样序列和优化预算。未使用的通道在归一化后清零。

**任何依赖未来 E 计算的高度、距离等特征，都只能放在未来分支，不能提前混进三组共享的 H/C。**

### 7.2 训练配置

下面是建议冻结的起始配置，不是对收敛速度的保证：

```yaml
fps: 30
wm_history: 4
evaluator_history: 4
future_horizon: 24

hidden_dim: 128
transformer_layers: 2
attention_heads: 4
dropout: 0.1
progress_bins: 10
stage_classes: 4

batch_size: 64
optimizer: AdamW
learning_rate: 0.0003
weight_decay: 0.0001
warmup_updates: 200
max_updates: 10000
gradient_clip: 1.0
validation_interval: 500

stage_loss_weight: 1.0
progress_loss_weight: 1.0
rewind_probability: 0.25
```

先做少量序列的过拟合检查，确认标签、掩码、梯度和时序正确，再进行三组正式对照。正式比较使用三个初始化种子，按同一验证规则选择检查点，不在测试集挑最好种子。

抽样顺序建议为：

**物体均衡 → 阶段均衡 → 序列 → 窗口。**

这样不会让某个物体或很长的保持片段占据训练。

### 7.3 数据划分

继承 PointWorld 实际使用的 GRAB 划分，不另起一套互相冲突的随机划分。

当前仓库定义了对象级验证、测试留出：验证对象包括 apple、toothbrush、elephant、hand；测试对象包括 mug、wineglass、camera、binoculars、fryingpan、toothpaste。需要继续核对它们与实际检查点的输入 manifest 一致。

这不是增加跨任务要求，而是避免评估器或 PointWorld 已经见过同一测试轨迹。某个留出物体没有符合条件的 lift 片段，就报告缺失，不能为了凑数量悄悄换划分。

### 7.4 主要指标

主要报告：

**逐物体、逐阶段的进度 MAE；阶段宏平均 F1；片段评分误差；真实时间顺序和倒退片段的评分变化。**

进度误差先在独立序列内平均，再按物体汇总。置信区间按原始序列聚类，不能把重叠窗口当作独立样本。

额外保留两个便宜但重要的对照：

| 对照 | 作用 |
|---|---|
| 根据当前状态做简单外推的进度预测 | 检查 Transformer 是否只是利用阶段与时间先验 |
| 不学习网络，直接用可计算几何条件评分 | 检查学习型 evaluator 的额外价值 |

**不同初始状态的片段排序，只能叫“进展排序”，不能叫同状态候选动作排序。**

## 八、怎样接入现有 PointWorld

### 8.1 先冻结，不联合训练

仓库记录主三源训练已完成，`best.pt` 对应 46,000 步，`final.pt` 对应 50,000 步。第一轮建议预先选定 `best.pt` 并核对哈希，不根据新测试结果在多个世界模型之间选最好。

保留检查点原来的输入输出归一化。评估器使用自己的训练集统计，不能顺便更改 PointWorld 的归一化 buffer。

### 8.2 必须先做“只替换输入”

对训练好的 Oracle-EI 评估器：

```text
原来：H + A + C + GT-E + GT-I
替换：H + A + C + Pred-E + Derived-I
```

评估器权重完全不变。

这是最清楚的一次测试：**物理预测误差到底损失了多少评分能力？**

之后才可以增加第二项实验：冻结 PointWorld，让评估器在其预测结果上适配训练。两者分别报告，不能把适配后的提升全部解释为世界模型更准确。

物理误差也要同时报告，至少包括目标物体位移/旋转误差，以及 8、16、24 帧处的结果。否则评分变差时无法判断问题来自预测还是评估器。

### 8.3 统一缓存

每个预测缓存绑定：

```text
原始序列及窗口身份
目标物体 slot
PointWorld 检查点哈希
模型配置与归一化版本
手点顺序、坐标系、掩码
标签版本
```

同一个窗口的 E/I 和标签必须按这些身份连接，不能依靠“两个文件行数一样”。

对候选推理还要增加**批次与排列不变性测试**。当前代码存在共同体素原点依赖，因此这一项必须在机器人候选评分前处理或量化；不能默认换了候选排列，预测就完全相同。

## 九、后续机器人架构如何闭合

这是整个方案最容易出现“离线成功、上线接不上”的地方。

### 9.1 GRAB 第一阶段的 A 是真实观测运动

因此应明确标记：

```text
action_semantics = measured_hand_trajectory
```

本轮结果只证明：

> 给定一条真实发生的手部运动，PointWorld 预测的物体未来是否能支持进度评价。

它还没有证明能够评价机器人提出的任意动作计划。

### 9.2 机器人阶段选择明确的计划式接口

我建议借鉴 DexWM：

```text
候选关节目标轨迹 q_plan
        ↓ FK
未来手部点轨迹 A_plan
        ↓ PointWorld
物体未来 E_pred
        ↓ 与 A_plan 组合
I_geo_pred
        ↓ Evaluator
候选评分
        ↓
执行选中目标轨迹的前 8 步，再重新规划
```

DexWM 同样是在关节空间生成候选、用 FK 转成手部动作，而不是直接任意修改手点坐标。[arXiv](https://arxiv.org/html/2512.13644v2)

候选可先围绕现有重定向参考轨迹生成，保留原参考候选，并遵守现有关节范围、耦合和速度约束。首版不需要立刻训练新的大规模动作生成模型。

**但不能把现在的“P0 未来闭环动作＋18维残差”直接称作这条 `q_plan`。** P0 后续依赖未来状态，其完整几何轨迹事前未知。若采用计划式控制器，对照基线也必须使用同一个候选生成器和执行接口，不能把控制器改变带来的差异归给世界模型。

### 9.3 目标轨迹不等于真实执行轨迹

FK 只能得到目标几何，不能保证实际手会精确走到那里。因此机器人接入前，需要一轮**普通连续 rollout 校准**，同时记录：

```text
A_plan       决策时已知的目标手轨迹
A_executed   实际测得的手轨迹
E_gt         实际物体运动
```

先检验目标与实际的差距。差距小，再验证世界模型；差距明显，先调整控制接口和候选范围。仍解决不了时，才需要执行预测或联合手物预测，不能继续拿目标轨迹冒充真实运动。

这里也有一个关键时序合同：

> **训练某条 24 步计划的执行后果时，要么真实执行完整 24 步，要么只监督它实际执行的部分。**

如果第 8 步就重规划，后 16 步已经属于另一条计划，不能将整段实际结果归到第一条 A24 上。校准采集可完整执行短计划；正式规划再采用“预测24步、执行8步”。

### 9.4 不需要重新 fork 才能评价最终收益

机器人阶段可以比较：

**同一候选生成器和执行器，不评分／E0评分／PointWorld＋Evaluator评分**，分别运行完整 episode，比较实际抓取完成率、保持表现和失败类型。

这不要求恢复中途物理状态，也不要求给每个候选都获得真实反事实结果。

只有当研究问题变成“同一个中间状态的所有候选，真实结果各是什么”时，才需要额外的重复执行或反事实采集。**它不应再成为本方案第一阶段的前置条件。**

## 十、仓库怎么改，才能不继续制造混乱

在当前 `consequence-evaluator` 下增加独立的 GRAB 进度模式，保留旧配对实验，**不改写旧数据，也不直接解除旧训练门槛**。

建议新增：

| 模块 | 职责 |
|---|---|
| `grab_progress_data.py` | 读取当前 GRAB 几何缓存及标签侧文件 |
| `grab_progress_labels.py` | 阶段边界、进度、有效性及标注版本 |
| `pointworld_adapter.py` | 构造 WM 输入、选目标物体、统一 E/I |
| `progress_model.py` | 几何编码器、时序主干、阶段/进度头 |
| `progress_metrics.py` | 序列/物体均衡评价、评分诊断 |
| `progress_contracts.py` | 张量、坐标系、动作语义与来源检查 |

对应新增准备、训练、Oracle 评估、预测替换四个入口即可，不必再建新的 Git 分支体系。

数据使用新的 schema，例如：

```text
ref2dex.grab-progress.v1
```

不要复用原先要求 `24×18 residual_plan` 和严格偏好配对的 schema。

最低限度的回归测试应覆盖：

**手点顺序、目标 slot、E/I 变换、原始帧号对齐、无效掩码、标签不进入输入、因果掩码、跨划分泄漏、GT→预测完整替换，以及重规划后的执行掩码。**

## 十一、执行顺序与停止条件

| 阶段 | 做什么 | 得到什么 |
|---|---|---|
| **A：数据闭合** | GRAB lift 筛选、阶段边界核查、标签侧文件、接口测试 | 一套可训练且时间对齐的数据 |
| **B：Oracle 对照** | E0、Oracle-E、Oracle-EI | 真实未来对进度评价的增量 |
| **C：预测替换** | 冻结 WM 与 evaluator，GT 换预测 | 当前 PointWorld 能保留多少能力 |
| **D：机器人适配** | 目标轨迹/FK、连续执行校准、机器人域验证 | 可执行的计划—预测—评分接口 |
| **E：控制收益** | 普通完整 rollout 对照 | 是否真的改善抓取 |

我建议按以下结果推进：

**Oracle 没有增益**：先检查 E0 是否已能完成任务、标签是否主要由时间决定，以及模型是否学得动。不要自动追加 PointWorld 训练。

**Oracle 有增益、预测替换后消失**：问题优先落在物理预测误差或表示分布差异，不重新定义 Y。

**预测替换保留增益**：进入机器人接口校准，而不是直接声称抓取成功率会上升。

**保持阶段所有候选分数都一样**：这可能是进度目标本身已经饱和。若后续目标是长期抗扰保持，必须补真实失败/稳定性监督；不能期待把网络加深就自动学会未被监督的风险。

## 最终建议

**这条路线值得做，但交付目标必须准确：先得到一个与 PointWorld 接口闭合的、学习型抓取进度评估器。**

它最有价值的地方是：不再依赖难以获得的严格状态配对，能复用 GRAB 和现有世界模型，同时把“物理未来是否有用”和“预测未来能否替代真实未来”分开验证。

现在真正应该开始的是 **GRAB 阶段标签＋统一几何接口＋三组小模型对照**。先不新增接触动力学网络，不训练长期 critic，不重做那批昂贵的 fork 实验。
