对，**完整链路基本已经成形了**。但我建议做两个关键修正，否则后面容易把不同问题混在一起。

完整流程最好拆成下面 5 个 Gate：

\[
\boxed{
\text{GT Value}
\rightarrow
\text{Oracle Evaluator}
\rightarrow
\text{PointWorld}
\rightarrow
\text{Execution Bridge}
\rightarrow
\text{Imagined MPC}
}
\]

### Gate 1：先证明 GT Value 本身有用

这一步甚至**先不要训练 evaluator**。

对于同一状态下的多个候选 \(A_i\)，用它们各自的 GT future 直接计算：

\[
Y_i^{GT}
=
P_{t+24}^{(i)}-P_t.
\]

然后直接：

\[
A^*=\arg\max_i Y_i^{GT}.
\]

滚动执行，看成功率是否从 baseline 提升，尤其看：

- baseline failure 能救回来多少；
- baseline success 会不会被搞坏；
- 总体 success rate 是否提升。

这一步证明的是：

\[
\boxed{\text{我们定义的 Value 标签本身有没有决策意义}}
\]

这比一上来训练 evaluator 更干净。

---

### Gate 2：再训练 Oracle Evaluator

训练：

\[
Q_\theta(R,H,A,Z^{GT})\rightarrow Y^{GT}.
\]

然后用：

\[
\arg\max_i Q_\theta(R,H,A_i,Z_i^{GT})
\]

替代直接使用 \(Y_i^{GT}\)。

这一步回答：

\[
\boxed{\text{GT future 中的价值能不能被模型学出来}}
\]

最好保留三个对照：

\[
Q(H,A)
\]

\[
Q(H,A,Z^{GT})
\]

以及 future shuffle。

否则 evaluator 可能直接从 \(H,A\) 猜价值，根本没用 GT future。

---

### 关于你说的“之前的 fork 数据”

这里要严格区分。

**可以用的是之前那套从 episode 初始状态完整 replay prefix，再在决策点执行不同 candidate 的数据。**

不能用的是：

\[
\text{mid-state PhysX snapshot restore}
\]

那条路线我们已经验证过并不等价。

之前那套 **32 个相同 decision prefix × 多候选、从初始状态完整重放** 的数据是科学上更可信的；如果其中保存了完整 hand/object future，就可以直接重新计算我们现在新的 \(Y^{GT}\)，不一定重新采。之前的 rolling GT-Y 实验其实已经出现过 baseline \(23/32\rightarrow27/32\) 的方向性结果，但那用的是旧 Y 定义，所以现在的新 reference-progress value 仍然需要重新验证。 

---

### Gate 3：PointWorld 换掉 GT future

Oracle 通过以后，再做：

\[
(H,A^{exec})\xrightarrow{\text{PointWorld}}\hat Z.
\]

这里用 Gym 机器人 rollout 微调 PointWorld 很合理。

但这一步**不要只看 EPE/RMSE**。

真正应该测：

\[
Q(H,A,\hat Z)
\]

相对于：

\[
Q(H,A,Z^{GT})
\]

还能保留多少 candidate ranking。

也就是：

\[
\boxed{\text{prediction error 是否真的破坏动作排序}}
\]

这是比“物体位置误差 8 mm”更重要的指标。

---

### Gate 4：解决执行与想象的 gap

这一步你说的 execute model 是必要的，但要把接口定义清楚。

最终实际链应该是：

\[
A^{desired}
\xrightarrow{\text{Execution Model}}
\hat A^{exec}
\xrightarrow{\text{PointWorld}}
\hat Z
\xrightarrow{\text{Evaluator}}
\hat Y.
\]

Execution Model 可以学习：

\[
(H,A^{desired})\rightarrow A^{exec}
\]

或者进一步输出 robot native command。

训练数据直接来自 Gym：

\[
A^{desired},\quad u,\quad A^{exec}.
\]

PointWorld 则最好用**实际执行 hand-flow**训练：

\[
(H,A^{exec})\rightarrow Z.
\]

这样职责很清楚：

- Execution model：预测“机器人实际上会怎么动”；
- PointWorld：预测“手真的这么动以后，物体会怎么动”。

不要让一个模型同时吞掉两个误差来源。

---

### Gate 5：最终验证“想象有没有帮助”

最终：

\[
A_i^{desired}
\rightarrow
\hat A_i^{exec}
\rightarrow
\hat Z_i
\rightarrow
\hat Y_i.
\]

选择：

\[
A^*=\arg\max_i\hat Y_i.
\]

然后只执行短前缀：

\[
K_{\rm exec}=4\sim8
\]

重新观测，再规划。

最终比较：

\[
\boxed{
\text{Baseline}
\quad vs\quad
\text{Direct }Q(H,A)
\quad vs\quad
\text{PointWorld imagination}
}
\]

在相同初始状态、相同 candidate budget 下比较 success rate。

---

所以你的整体想法是对的，但我会把它稍微修正成：

\[
\boxed{
\begin{aligned}
1.&\ \text{直接 GT Value 选择候选，证明标签有用}\\
2.&\ \text{GT future → Evaluator，证明 oracle evaluator 可学}\\
3.&\ \text{PointWorld 替换 GT future，证明预测 future 仍保留排序信息}\\
4.&\ \text{Execution Model 修正 desired→executed gap}\\
5.&\ \text{闭环滚动执行，最终证明 imagination 比不用 imagination 好}
\end{aligned}
}
\]

这里最关键的是**第 1 步和第 2 步不要合并**。否则如果 oracle evaluator 失败，你不知道是：

- Value 标签本身没用；
- 还是 evaluator 没学好。

而一旦第 1 步明确成功，后面的整个研究就会变成非常清晰的“逐级逼近 oracle”：

\[
\boxed{
GT\ Value
\rightarrow
GT\ future
\rightarrow
predicted\ future
\rightarrow
executable\ predicted\ future
}
\]

我认为这就是目前最完整、也最容易定位失败原因的一条主线。
